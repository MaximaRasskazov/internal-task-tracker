## Что меняют дополнительные условия курса

В исходном мини-ТЗ Docker Compose рекомендован. В присланной теме 5 уже требуется показать Dockerfile, Compose и конфигурацию CI/CD, успешные контейнеры и пройденный pipeline. Поэтому контейнеризация и автоматическая проверка становятся частью плана сдачи.

Тема 4 отдельно требует настроенные линтеры/форматировщики, объединенную структуру проекта и доказательство успешной проверки линтером. Итоговый контроль отдельно требует презентацию.

Номер темы определяет содержание отчета. Он не требует сначала построить весь сервер без продуманной БД, а затем переписывать его. Модель, миграции, линтеры и минимальный CI следует вводить с начала разработки и описывать в соответствующих отчетах по мере готовности.

## Тема 1. Backend

**Что необходимо предоставить по присланным условиям:**

- Ссылку на репозиторий или ветку с актуальным серверным кодом.
- Язык, серверный фреймворк, ключевые библиотеки и краткое обоснование.
- Дерево серверной части с назначением маршрутов, контроллеров, моделей и других основных модулей.
- Скриншоты успешных запросов через Postman/Swagger либо работающего сервера.

**Предлагаемое содержательное доказательство:** вход, защищенный запрос, создание проекта/доски/задачи, отказ постороннему пользователю. В отчете явно перечислить, какие функции готовы на этом этапе и какие остаются до итоговой сдачи.

## Тема 2. База данных

**Что необходимо предоставить:**

- Ссылки на миграции, конфигурацию БД или ORM-модели.
- СУБД и ORM/драйвер с обоснованием.
- Дерево модулей хранения, ER-диаграмму и описание таблиц и связей.
- Скриншоты заполненных таблиц из клиента БД либо успешного выполнения миграций.

**Предлагаемое содержательное доказательство:** создание схемы на пустой БД, демонстрационные данные, сохранение изменений после перезапуска, ограничения связей между проектами и атомарное перемещение. Не допускать расхождения ER-диаграммы и фактической схемы.

## Тема 3. Frontend

**Что необходимо предоставить:**

- Ссылку на исходный код клиента.
- Фреймворк/библиотеку, сборку и стилизацию с обоснованием.
- Дерево страниц, компонентов и сервисов взаимодействия с API.
- Скриншоты ключевых страниц, желательно с Network и успешными обращениями к серверу.

**Предлагаемое содержательное доказательство:** доска, подробная карточка с историей и комментариями, фильтры, аналитика; сценарий узкого экрана. Данные для скриншотов создаются через seed или интерфейс, а не подставляются вместо работающего API.

## Тема 5. Docker и CI/CD

**Что необходимо предоставить:**

- Ссылки на Dockerfile, Compose и `.github/workflows/*` при выборе GitHub Actions.
- Фактически использованные версии Docker, базовые образы и платформу CI/CD.
- Дерево конфигураций и описание взаимодействия Frontend → Backend → DB.
- Скриншот запущенных контейнеров через `docker ps`.
- Скриншот успешного pipeline в Actions при выборе GitHub Actions.

**Предлагаемое содержательное доказательство:** контейнеры запускаются по README; приложение доступно браузеру; БД сохраняет данные в томе; API и WebSocket доступны через согласованный маршрут. Полный сквозной сценарий выполняется после чистого развертывания.

Для Windows и macOS необходимо отдельно зафиксировать рабочий путь запуска. Совместимость конфигурации с обеими платформами не следует объявлять проверенной до фактических запусков. Если используются образы с несколькими архитектурами, при выборе тегов проверить доступность нужных вариантов.

Условия требуют автоматической проверки обновлений репозитория. Публичный сервер и автоматическая публикация в production не названы обязательными: способ размещения демо определяется отдельно.

## Итоговая защита

Итоговая презентация должна объяснять фактически реализованный продукт. Предлагаемый порядок на 5–10 минут:

1. Проблема, пользователи и роли — до 40 секунд.
2. Схема клиент/API/БД/WebSocket и ключевые связи данных — около минуты.
3. Создание или открытие проекта, доски и кастомной колонки — около минуты.
4. Задача с исполнителем, сроком, Story Points; перемещение и сохранение после refresh — около минуты.
5. Второй пользователь получает изменение; показывается история и комментарий — около минуты.
6. Три одновременно работающих фильтра и два графика — около минуты.
7. Отказ постороннему пользователю, reconnect и объяснение конфликтов — около минуты.
8. Тесты, CI, чистый запуск и вклад каждого — оставшееся время.

Точные действия, учетные записи и ожидаемые значения графиков фиксируются после согласования seed. При репетиции сценарий измеряется секундомером; последовательность сокращается до отведенного преподавателем времени без потери обязательных доказательств.

## Правила сбора доказательств

- Для каждого отчета сохранять ссылку на конкретный коммит или тег; ветка со временем меняется.
- Скриншот должен соответствовать версии кода, указанной в отчете.
- Версии инструментов брать из фактического окружения, а не вписывать предполагаемые числа.
- На скриншоты и в Git не должны попадать реальные секреты и токены.
- Не выдавать предложенную структуру каталогов за существующую: дерево строится по готовому репозиторию.
- Не использовать зеленый pipeline другого коммита как доказательство готовности текущего.
- Мини-отчет — короткий материал с проверяемыми ссылками и доказательствами; объем страницы преподавателем не задан.
