# Frontend — реализация и запуск

Vue 3 + TypeScript + Vite, Pinia, Vue Router, PrimeVue 4. Светлая тема с цветными акцентами в направлении «Зефир». Зависимости фиксируются package-lock.json.

## Запуск

Нужен Node.js 24. Из этой папки:

```powershell
npm ci
npm run dev
```

Открыть http://localhost:5173. API и базу запустить отдельно по корневому README. Порт 5173 фиксирован, поскольку входит в разрешенные Origin бэкенда. Vite проксирует `/api` и `/ws` на `http://127.0.0.1:8000`, сохраняя Origin.
Для другого адреса API скопировать `.env.example` в `.env.local` и изменить `API_PROXY_TARGET`. Секреты сервера в frontend не копировать.

Если PowerShell блокирует npm.ps1, использовать `npm.cmd` вместо `npm`.

## Что готово к ручной проверке

- Регистрация (после нее нужен вход), вход, восстановление сессии, выход.
- Проекты с пагинацией, создание проекта для pm/admin.
- Доски и участники проекта с пагинацией; создание доски для владельца/admin.
- Просмотр реальной доски: колонки, задачи, приоритет, исполнитель, срок и SP.
- Мобильная навигация, loading/empty/error, безопасный returnTo, ошибки форм и ожидание после 429.

Добавлены создание, редактирование и удаление задач, подробная панель, выбор существующих тегов и прямая ссылка /tasks/:taskId. Доска обновляется через WebSocket; при потере связи записи временно блокируются. Добавлены комментарии, история изменений и управление тегами. Добавлены перетаскивание и выбор положения задачи через окно «Переместить». Добавлены поиск и комбинируемые фильтры с сохранением условий в URL. Добавлены настройки проекта/доски, участники и администрирование ролей. Добавлена аналитика проекта с двумя графиками и точными значениями. Добавлена контейнерная упаковка; финальная браузерная приёмка остаётся пользователю.

## Сценарии проверки

1. Войти как pm@example.test с DEMO_PASSWORD из локального .env; открыть проект и доску.
2. Перезагрузить страницу: сессия восстанавливается. Выйти и проверить защищенную прямую ссылку.
3. Создать проект с уникальным ключом и доску; обновить страницу и убедиться в сохранении.
4. Войти как developer: кнопка создания проекта отсутствует; доступны только разрешенные проекты.
5. Зарегистрироваться: роль developer, после регистрации появляется форма входа.
6. Остановить API и проверить понятную ошибку. Запустить его и повторить чтение.
7. Проверить ширины 390/768/1440, Tab, Esc в диалоге и видимость фокуса.

## Автоматические проверки

```powershell
npm run api:generate
npm run api:check
npm run typecheck
npm run lint
npm run format:check
npm run test:unit -- --run
npm run build
```

DTO генерируются из ../docs/api/openapi.json. Generated-файл не редактировать вручную. HTTP-клиент передает cookie и CSRF, обрабатывает 204 и не повторяет записи после сетевой ошибки. JWT/CSRF не сохраняются в localStorage. Tests используют управляемые ответы fetch и не заменяют проверку с PostgreSQL.

Сервер разработки, Docker и браузерная приемка оставлены пользователю по договоренности. Полный T07 считается интегрированным после ручных сценариев и review.

## Проверка этапа 2 — задачи

1. Открыть доску и нажать «Новая задача» или «Добавить задачу» в колонке.
2. Заполнить название, описание, приоритет, исполнителя, срок, SP и существующие теги. Создать; обновить страницу и проверить данные.
3. Нажать на карточку, изменить несколько полей и сохранить. Очистить исполнителя, срок, SP и теги; убедиться после обновления, что значения очищены.
4. Ввести текст и закрыть панель крестиком, Esc или кнопкой браузера «Назад»: появляется подтверждение. Отмена оставляет введенный текст.
5. Открыть постоянную ссылку на задачу в новой вкладке: должна открыться ее доска и панель.
6. В двух независимых сессиях открыть одну задачу. Сохранить правку в первой, затем во второй: ожидается конфликт с сохранением черновика. Сверить данные сервера, выбрать «Сохранить мои правки в форме», проверить значения и нажать «Сохранить».
7. Удалить задачу под автором/руководителем/admin, подтвердив диалог. У другого обычного участника кнопки удаления чужой задачи нет.
8. При сетевой ошибке записи не повторять создание вслепую: проверить доску. Для редактирования доступны перечитывание и явная сверка. Форма сама не повторяет запись.

Дедлайн передается календарной датой без UTC-преобразования. Изменить колонку и порядок существующей задачи можно перетаскиванием или через кнопку «Переместить» на доске. Комментарии и история доступны в нижней части панели задачи.

## Проверка этапа 3 — обсуждение, история и теги

1. Обновить приложение, открыть задачу: под формой доступны «Обсуждение» и «История».
2. Написать многострочный комментарий. Enter добавляет строку, Ctrl/⌘ + Enter отправляет. Проверить автора, время, сохранение после обновления страницы. HTML в тексте должен отображаться как текст.
3. Начать новый комментарий, переключиться на историю и вернуться: черновик сохранён. Попробовать закрыть панель и перейти назад: требуется подтверждение потери текста.
4. Изменить поля задачи и открыть историю. Развернуть «Было / Стало», проверить пустые значения, SP=0, исполнителя и теги. Время показано в timezone проекта.
5. Для обсуждения с более чем 20 комментариями проверить страницы; для длинной истории — «Загрузить следующие события». Черновик комментария остаётся при смене страницы.
6. На доске нажать «Теги» или в задаче «Управление тегами». Создать тег с названием и цветом, назначить задаче и проверить цвет на доске.
7. Под владельцем проекта/admin переименовать тег и изменить цвет. Под обычным участником доступно создание, но нет кнопок редактирования и удаления.
8. Создать дубликат имени: ожидается ошибка с сохранением формы. Попробовать удалить используемый тег: сервер должен отказать. Ссылки из удалённых задач тоже препятствуют удалению. Удалить отдельный неиспользуемый тег.
9. Проверить закрытие окна тегов и переход назад с несохранённым названием: отмена подтверждения сохраняет форму.
10. При неопределённом результате записи (сетевая ошибка/5xx) повторная отправка блокируется. Обновить список, проверить результат, затем явно разрешить повтор, только если операция не сохранилась.
11. Скопировать постоянную ссылку задачи, удалить задачу и открыть ссылку: авторизованному участнику доступна история удалённой задачи (время в UTC).
12. Проверить узкий экран, прокрутку панели, Tab и Esc. Изменения другой сессии автоматически поступают через WebSocket (этап 4).

Автоматические тесты используют управляемые ответы API. Проверка с Docker/PostgreSQL и браузерная приёмка выполняются пользователем.

## Проверка этапа 4 — обновления в реальном времени

1. Открыть одну доску в двух независимых сессиях (обычное и приватное окно). Дождаться «Обновляется автоматически».
2. В первой сессии создать/изменить/удалить задачу, добавить комментарий, переименовать тег. Во второй проверить карточки, обсуждение, историю и теги без перезагрузки.
3. Открыть одну задачу в обеих сессиях. Без местных правок поля обновляются автоматически. С местным черновиком чужое изменение предлагает сверку; введённый текст сохраняется. Проверить оба варианта сверки.
4. Отключить сеть (DevTools Offline либо остановить API). После разрыва/35 секунд тишины виден статус потери соединения, новые записи недоступны, снимок и черновики остаются. Вернуть сеть: после reconnect и свежего снимка запись снова разрешена.
5. Пока вторая сессия отключена, сделать несколько изменений в первой. После возврата связи проверить, что получено актуальное состояние, даже если отдельные события пропущены.
6. Удалить участника с открытой доской: доступ закрывается, доска скрывается, бесконечного reconnect нет. Проверить истечение сессии/выход в соседней вкладке: должен появиться вход. Удаление доски также прекращает reconnect.
7. Открыть Network → WS: URL /ws/v1/boards/{id}, без токенов в query. Видны connection.ready и heartbeat. После ухода с доски соединение закрывается.
8. Убедиться, что восстановление связи не повторяет автоматически ранее отправленные POST/PATCH/DELETE.

Для локального запуска уже настроен Vite proxy /ws. Production reverse proxy также должен проксировать WebSocket Upgrade и сохранять Origin; адрес приложения должен быть в allowed_origins backend. Новые зависимости и миграции не нужны.

## Проверка этапа 5 — перенос задач и порядок

1. Перетащить задачу в другую колонку: перед карточкой, в конец и в пустую колонку. Место вставки подсвечивается; пока запрос выполняется, карточка отмечена пунктиром.
2. Изменить порядок внутри одной колонки. Обновить страницу и проверить сохранённый порядок. Перенос на прежнее место не должен отправлять запись.
3. Нажать «Переместить» у карточки, выбрать колонку и положение «Перед …» либо «В конец колонки». Выполнить сценарий клавиатурой (Tab, Enter, Esc) и на телефоне без перетаскивания.
4. Перенести задачу в done и обратно: проверить завершённость и события истории. Вторая независимая сессия получает новый порядок автоматически.
5. Начать перетаскивание, затем изменить ту же задачу в другой сессии и завершить перенос. При конфликте UI перечитывает доску; предварительное положение не затирает новый снимок. Перенос сам не повторяется.
6. Проверить перенос при изменении/удалении карточки, перед которой выполняется вставка. Если место уже изменилось, выбрать его заново; сервер может вернуть POSITION_CONFLICT.
7. При сетевом сбое после отправки проверить порядок на сервере и нажать «Проверил: разрешить новый перенос» только после сверки. Пока результат неизвестен, новые переносы заблокированы. Не повторять перенос вслепую.
8. Пока перенос сохраняется, повторные переносы и редактирование задачи недоступны. При offline перетаскивание и отправка из окна также недоступны.
9. Проверить узкий экран 390 px, горизонтальную прокрутку доски и фокус после закрытия окна. Для touch использовать кнопку «Переместить».

Перенос передаёт column_id, before_task_id (null = конец) и expected_version. Индексы видимых карточек не используются. Для переноса при активных фильтрах добавлены автоматические проверки в этапе 6; ручные сценарии описаны ниже.

## Проверка этапа 6 — поиск и фильтры

1. Раскрыть «Поиск и фильтры». Найти задачу по части названия или ключу, например TEAM-12. Нажать «Применить» или Enter.
2. Проверить исполнителя, «Не назначен», теги, приоритеты, колонки и срок. Выбрать минимум три вида условий вместе. Для тегов нужны все выбранные теги; приоритеты и колонки допускают любой выбранный вариант.
3. Проверить обе границы срока, включая одинаковые даты. Задачи без срока не попадают в выборку при заданной границе. Обратный диапазон должен блокировать применение.
4. Обновить страницу, скопировать ссылку в другую авторизованную сессию, пройти Назад/Вперёд: условия восстанавливаются из URL. Сброс возвращает все задачи и сохраняет query-параметр открытой карточки.
5. Получить пустой результат: видны пояснение и пустые колонки, доступные для переноса. Проверить неизвестный ID/некорректную дату в ссылке — понятная ошибка и возможность сброса.
6. При активном фильтре перенести задачу перед видимой карточкой. После сброса проверить общий порядок, включая скрытые карточки. Перенос в конец означает конец всей колонки.
7. Выбрать одну колонку фильтром и перенести задачу в другую: задача исчезает из выборки с пояснением «Задача перемещена и скрыта текущим фильтром».
8. Изменить подходящую задачу в другой сессии так, чтобы она перестала соответствовать условиям: выборка обновляется через синхронизацию доски. Открытая форма и её черновик не заменяются отфильтрованным списком.
9. При медленной сети быстро применить разные условия: запоздавший ответ не должен заменять последнюю выборку. При ошибке доступна кнопка повторного поиска; перенос заблокирован до согласованной выборки.
10. Проверить фильтры на ширине 390 px, клавиатуру, названия полей и кнопку сброса. Фильтрация выполняет GET-запросы и не меняет данные задач.

Пресеты фильтров и WIP-подсказки относятся к дополнительному объёму и в этот этап не входят. Браузерная проверка с реальным API остаётся пользователю.

## Проверка этапа 7 — настройки и администрирование

1. Под руководителем проекта/admin открыть проект → «Настройки проекта». Изменить название/описание, сохранить и проверить после обновления. Ключ и timezone показываются без редактирования по контракту API.
2. Добавить зарегистрированного пользователя по email. Повторное добавление не создаёт дубль. Для незарегистрированного email ожидается ошибка с сохранением введённого значения.
3. Проверить страницы участников. Удалить обычного участника, отменив подтверждение, затем подтвердив его. Руководителя нельзя удалить напрямую.
4. Передать руководство активному участнику. Под прежним владельцем без роли admin управление должно стать недоступным. Убедиться в изменении прав в другой сессии.
5. На доске открыть «Настройки доски». Переименовать её; создать колонки todo/in_progress/done; переименовать существующую. Категория существующей колонки заблокирована.
6. Кнопками вверх/вниз изменить порядок колонок, вернуться на доску и обновить страницу. В двух сессиях изменить структуру/задачи до попытки сохранения порядка: возможен VERSION_CONFLICT, требуется обновление и явное разрешение новой операции.
7. Попробовать удалить непустую колонку: сервер должен отказать, включая случаи сохранённой истории удалённых задач. Удалить отдельную пустую колонку. Доска удаляется после удаления всех колонок; проект — после удаления его досок и тегов.
8. Под admin открыть «Пользователи» в боковом или мобильном меню. Проверить поиск имени/email и страницы. Отменить смену роли, затем подтвердить её для другого пользователя. Собственная роль недоступна для изменения; последнего администратора защищает сервер.
9. Под developer/чужим pm открыть прямые ссылки настроек и /admin/users: операции не должны быть доступны. Ошибки 403/409 от сервера должны оставаться понятными, без потери введённых данных.
10. Проверить несохранённый текст: переход назад/на другой экран требует подтверждения. При неопределённом результате записи обновить данные, проверить итог и только затем разрешить новую операцию. Автоматического повтора нет.
11. Проверить ширину 390 px, клавиатуру и доступность кнопок порядка/удаления. Проверка в браузере с реальным API выполняется пользователем; автоматические тесты используют управляемые ответы.

Новые миграции и зависимости для этого этапа не нужны. Все изменения прав и удаление объектов выполняются только при соответствующих действиях пользователя в интерфейсе.

## Проверка этапа 8 — аналитика проекта

1. Открыть «Аналитика проекта» на странице проекта или «Аналитика» на доске. Проверить доступ обычного участника и администратора, а также отказ при отсутствии доступа к проекту.
2. Переключить «7 дней», «30 дней», «Всё время». Период сохраняется в URL; обновление страницы и Назад/Вперёд восстанавливают выбор. Границы и timezone берутся из ответа сервера.
3. Сверить «Задачи по колонкам» с досками. Колонки с одинаковыми названиями разных досок показываются отдельно. Удалённые задачи исключены; график отражает текущее состояние независимо от выбранного периода.
4. Перенести задачу в done, открыть аналитику и нажать «Обновить». Первое завершение должно появиться в соответствующем дне часового пояса проекта.
5. Вернуть ту же задачу в работу и повторно завершить: счётчик первых завершений не увеличивается. Удаление задачи не убирает её первое завершение из исторического графика.
6. Проверить проект без задач и период без завершений. Появляются понятные пустые состояния; нулевая серия не вызывает ошибки графика.
7. Раскрыть «Показать точные значения», проверить нули и пагинацию. Для длинной истории используется серверная группировка по месяцам; подписи и таблица должны ей соответствовать.
8. При медленной сети быстро менять период: старый ответ не заменяет выбранный. При ошибке API статистика скрывается и доступна повторная загрузка.
9. Проверить ширины 390/768/1440 px, клавиатуру, подписи и читаемость чисел. Цвет дополняет названия и значения, а не заменяет их.

Новых библиотек, миграций и команд запуска не требуется. Обновление аналитики выполняется кнопкой «Обновить» и при смене периода. Проверка реальных расчётов с API/PostgreSQL и визуальная приёмка остаются пользователю.

## Запуск собранного фронтенда в Docker

Из корня репозитория с уже подготовленным `.env`:

```powershell
docker compose --profile web up -d --build
```

Открыть http://localhost:8080. Сервис frontend собирает Vite-приложение и отдаёт его через Nginx; API и WebSocket доступны через тот же адрес. `npm run dev` в этом режиме не нужен. Миграции запускает существующий сервис migrate. Демоданные создаются отдельно по корневой инструкции, автоматически не добавляются.

В существующем `.env` параметр ALLOWED_ORIGINS должен включать точный адрес http://localhost:8080 (и http://127.0.0.1:8080, если используете его). Новые значения по умолчанию Compose не заменяют явно заданное значение в `.env`. При WEB_PORT, отличном от 8080, нужно добавить соответствующий Origin. Для локального HTTP используется COOKIE_SECURE=false; внешний HTTPS требует отдельной конфигурации TLS и COOKIE_SECURE=true.
