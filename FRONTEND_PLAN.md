# План фронтенда Internal Task Tracker

Подготовлен 3 ноября 2026 года для Саяна. Основа: ветка `develop`, коммит `e987fe6ea292fb78dff5b4e60feb5f40b6aab7e0`.

Это план реализации, а не отчет о готовности интерфейса. Репозиторий скачан в `internal-task-tracker/`. Изучены спецификация, передача фронтенду, OpenAPI, DTO, маршруты, проверки доступа, реализация WebSocket, серверные тестовые сценарии и отчеты. Сервер, контейнеры и тесты в рамках этого анализа не запускались.

## 1. Что уже есть и что предстоит сделать

В репозитории есть FastAPI-бэкенд с PostgreSQL, миграциями, демоданными, 40 HTTP-операциями в OpenAPI и WebSocket доски. Каталога `frontend/` пока нет. В текущем Compose предусмотрены БД, миграции, сервер и seed; клиент и Nginx предстоит добавить.

Система — корпоративный трекер задач:

- Пользователь входит в систему и видит доступные проекты.
- Проект содержит участников, несколько досок и общие теги.
- Доска содержит колонки и задачи; категория колонки определяет завершенность задачи.
- Задачу можно создавать, изменять, назначать, перемещать и комментировать; действия отражаются в истории.
- Пользователи видят изменения коллег, фильтруют задачи и открывают аналитику проекта.
- Администратор управляет глобальными ролями; руководитель проекта управляет его структурой и участниками.

В старых документах встречаются утверждения «кода пока нет» и базовая ветка `release`. Они не описывают скачанную ветку `develop`. План основан на фактическом коде и действующих контрактах; направление будущего PR нужно сверить с процессом команды. Рабочая ветка пользователя — `develop-front`.

| Кто владеет состоянием | Что хранит и за что отвечает |
|---|---|
| Session store | Пользователь, CSRF, срок сессии, восстановление и очистка |
| Board store | Полный серверный снимок, примененная revision, ожидающие операции; принятие свежих данных |
| `useBoardRealtime` в board | Соединение, heartbeat, reconnect и сигнал перечитать данные; закрытие при уходе со страницы |
| `useBoardFilters` в board | Разбор URL, серверная выборка, защита от ответов старых запросов |
| `useTaskDraft` в task | Черновик формы, dirty-state, ошибки полей, сохранение и конфликт |
| Компоненты | Локальное раскрытие меню, фокус, состояние диалогов |

Страницы собирают эти возможности. HTTP-запросы не размазывать по шаблонам; WebSocket не должен сам управлять формами. Серверный снимок и несохраненный пользовательский текст хранить отдельно.

## 3. Карта экранов

| Экран | Маршрут | Содержание |
|---|---|---|
| Вход | `/login` | Email, пароль, ошибка входа, переход к регистрации |
| Регистрация | `/register` | Имя, email, пароль, подтверждение; после успеха переход ко входу |
| Проекты | `/projects` | Доступные проекты, пагинация, создание по правам |
| Проект | `/projects/:projectId` | Доски, участники, переходы к настройкам и аналитике |
| Доска | `/projects/:projectId/boards/:boardId` | Колонки, задачи, фильтры, создание, связь |
| Прямая ссылка на задачу | `/tasks/:taskId` | Загрузка задачи и ее доски, открытие общей панели задачи |
| Аналитика | `/projects/:projectId/analytics` | Два графика, период, таблицы значений |
| Настройки проекта | `/projects/:projectId/settings` | Проект, участники, владелец, доски, колонки, теги |
| Пользователи | `/admin/users` | Каталог и изменение глобальных ролей |

Открытая карточка доски обозначается `?task=<id>`. Back и закрытие панели сохраняют фильтры. При переходе на доску проверять, что `projectId` в адресе совпадает с проектом полученного снимка.

Основной макет уже задан спецификацией: левая навигация около 232 px, верхняя панель 64 px, колонки около 300 px, подробная карточка справа около 520 px. На телефоне навигация и фильтры открываются панелями, задача занимает весь экран. Горизонтальная прокрутка ограничена рабочей областью доски.

## 4. Пошаговая реализация

Каждый этап заканчивается проверяемым пользовательским результатом. Указанные Txx связывают работу с существующим TEAM_ROADMAP; серверные части этих карточек заново выполнять не нужно.

### Шаг 0. Подготовить ветку и проверить сервер

Если работа начинается в только что скачанной копии, создать `develop-front` от `develop`. Если такая ветка уже существует, перейти на нее и проверить состояние перед изменениями. Не пересоздавать ветку с существующей работой.

Выполнить актуальные команды README. Основной Docker-путь:

```powershell
cd backend
uv sync --frozen
uv run python -m app.cli.init_env
cd ..
docker compose config --quiet
docker compose up --build --wait backend
docker compose run --rm seed
```

В README есть контейнерный способ создать `.env` без uv на хосте. Использовать имя сервиса `backend`: старые примеры с `api` из спецификации не соответствуют Compose.

Проверить `/api/v1/health/ready`, Swagger `/docs`, вход и получение проектов/доски. В seed есть `pm@example.test`, `dev-a@example.test`, `dev-b@example.test`, `admin@example.test` и посторонние пользователи. Пароль брать из локального `.env`, не переносить в исходники и отчет.

**Готово:** API отвечает, PM видит TEAM, участник открывает доску, посторонний не получает доступ. Дальнейшая интеграция не зависит от ручного заполнения БД.

**Готово:** приложение запускается, запрос через proxy доходит до API, типы проверяются, ошибки приходят в едином виде. Ответ 204 не вызывает ошибку JSON-парсинга.

### Шаг 3. Регистрация, вход и восстановление сессии — T07

API: `POST /auth/register`, `POST /auth/login`, `GET /auth/me`, `POST /auth/logout` с префиксом `/api/v1`.

- Реализовать формы регистрации и входа; `password_confirm` проверять только на клиенте.
- Учесть: регистрация возвращает UserDto, а не SessionDto, и сама по себе не выполняет вход.
- После входа хранить пользователя и CSRF в памяти Pinia. JWT остается в HttpOnly cookie.
- Перед открытием защищенного маршрута восстановить сессию через `/auth/me`; не делать преждевременный redirect во время проверки.
- На 401 очистить сессию и проектные данные, закрыть сокет, перейти ко входу с безопасным локальным адресом возврата.
- При 429 показать ожидание по `Retry-After`. На ошибку входа не запускать общий redirect повторно.
- Обновлять данные о роли через `/auth/me` при возвращении фокуса и переходах между разделами с объединением параллельных проверок.

**Готово:** вход, refresh и выход работают; неверный пароль объяснен; защищенная ссылка после входа открывается; токенов нет в localStorage.

### Шаг 6. Создание и редактирование задачи — T08

API: `POST /boards/{id}/tasks`, `GET /tasks/{id}`, `PATCH /tasks/{id}`, `DELETE /tasks/{id}?expected_version=...`.

- Сделать форму создания и общую панель подробной задачи для доски и прямой ссылки.
- Поля: title, description, priority, assignee, deadline, story_points, tag_ids; column_id выбирается при создании, последующий перенос выполняется отдельной операцией move.
- Показать автора, ключ, даты создания/изменения как данные для чтения.
- Валидировать по DTO: title до 200 символов, description до 20 000, SP — целое 0–100, не более 20 тегов. Авторитетная валидация остается на сервере.
- PATCH отправляет изменившиеся поля и исходную expected_version. Пропуск сохраняет значение; null разрешен только для assignee_id, deadline, story_points. Для очистки описания отправлять пустую строку, тегов — пустой массив.
- Сохранять форму явно кнопкой; предупреждать о несохраненном тексте при закрытии.
- Обрабатывать 409 без перезаписи чужих изменений: сохранить черновик отдельно, загрузить текущую задачу, дать пользователю сверить и повторно сохранить выбранный результат с новой версией.
- Удаление подтверждать по ключу и названию; кнопку показывать admin, руководителю или автору задачи.

**Готово:** задача создается и редактируется с сохранением после refresh; ошибка не стирает форму; два пользователя получают понятный конфликт вместо незаметной потери данных.

На этом месте достигается первая рабочая версия: вход → проект → доска → создание и изменение задачи. Это контрольная точка, но еще не полный релиз.

### Шаг 8. WebSocket и согласование данных — клиентская часть T09

Адрес: `/ws/v1/boards/{board_id}`. Это нативный WebSocket; бизнес-команды продолжают идти через REST.

- После `connection.ready` запросить снимок; сразу учитывать приходящие события.
- Хранить applied_revision и highest_seen_revision; события используют поле board_revision.
- Не заменять свежие данные старым снимком или ответом мутации. Если снимок отстает от увиденной revision — перечитать его.
- Дедуплицировать события по event_id; не считать revision уникальным ID события.
- Объединять перечитывания при серии событий: задержка 100 мс, максимальное ожидание 500 мс согласно спецификации.
- Обновлять также открытые комментарии/историю и активную серверную выборку. Не перетирать черновик формы.
- Проверять revision heartbeat, приходящего раз в 15 секунд; после 35 секунд без сообщений считать связь потерянной.
- Reconnect: 1, 2, 4, 8, 15 секунд, затем 15, с jitter ±20%; после восстановления снова ready → снимок → сверка.
- На 4401 отправлять ко входу; на 4403 очищать проектные данные; на 4404 возвращать к проекту. Бесконечный reconnect для этих причин запрещен.
- При недоступности соединения сохранять видимые данные и текст, блокировать новые изменения, не создавать очередь offline-записей.
- При отказе handshake браузер может не предоставить прикладной close code; тогда проверить `/auth/me` и доступ к доске HTTP-запросом, не предполагать, что каждое закрытие — временный сбой.

**Готово:** две независимые сессии сходятся после изменения; reconnect восстанавливает снимок; отзыв доступа удаляет закрытые данные из интерфейса.

### Шаг 9. Перемещение через меню и drag-and-drop — T11

API: `POST /tasks/{id}/move` с `column_id`, `before_task_id`, `expected_version`.

- Сначала сделать доступное меню «Переместить» с выбором колонки и начала/конца.
- Затем подключить SortableJS через один Vue-адаптер, который преобразует drop в ту же команду.
- Отправлять ID карточки-якоря; null означает конец полной целевой колонки. Не отправлять индекс массива или самостоятельно вычисленную position.
- Держать подтвержденный снимок отдельно от временного отображения переноса; разрешать одну ожидающую операцию на задачу.
- При отказе откатить временное положение к последнему подтвержденному состоянию и синхронизироваться. При неизвестном результате сетевого запроса сначала перечитать данные, а не повторять запись автоматически.
- Обрабатывать VERSION_CONFLICT и POSITION_CONFLICT, сохраняя актуальные обновления других пользователей при откате.

**Готово:** перенос внутри/между колонками и в пустую колонку сохраняется после refresh и виден второму пользователю; ошибка не оставляет ложный порядок. Полное закрытие T11 — после шага 10.

### Шаг 10. Серверные фильтры и перенос с фильтрами — T15, завершение T11

API: `GET /boards/{id}/tasks` → TaskList с board_revision.

- Добавить исполнителя/«Не назначен», теги, диапазон срока, приоритеты, колонки и текстовый поиск.
- Сохранять фильтры в URL, поддерживать Back, refresh, сброс и совместимость с query-параметром task.
- Массивы передавать повторяемыми параметрами: `tag_ids=id1&tag_ids=id2`.
- Между видами условий — AND; все теги обязательны; приоритеты и колонки — OR внутри соответствующей группы.
- Разделить полный снимок доски и отображаемую серверную выборку, проверять их revisions; поздний ответ предыдущего поиска не применять.
- Показывать «видно / всего» и отдельное состояние пустого результата.
- В переносе использовать видимый якорь; после последней видимой задачи — конец полной колонки. Скрытые задачи не переставлять.
- Если после перемещения задача перестала отвечать фильтру, объяснить ее исчезновение.

**Готово:** три и более вида фильтров работают одновременно; общая ссылка воспроизводит выборку; перенос с фильтром не повреждает порядок скрытых задач.

### Шаг 11. Управление проектом и администрирование — T18

- Настройки имени/описания проекта; key и timezone отображать без редактирования.
- Добавление зарегистрированного участника по точному email, удаление участника, передача владения.
- Создание/переименование/удаление досок; создание/переименование/удаление и порядок колонок.
- Для порядка колонок отправлять полный column_ids и expected_revision; устаревший порядок обрабатывать как конфликт.
- Категория колонки выбирается при создании и далее не изменяется.
- Управление тегами с обработкой DUPLICATE_TAG и TAG_IN_USE.
- Admin: список пользователей и смена роли другого пользователя. Не добавлять операции блокировки или редактирования профиля без соответствующего API.
- Объяснять PROJECT_NOT_EMPTY, BOARD_NOT_EMPTY и ограничения удаления колонок; не выполнять скрытый каскад удалений.

**Готово:** управляющий настраивает проект без Swagger; обычному участнику доступны только разрешенные действия; серверный отказ корректно отображается даже при устаревших правах в UI.

### Шаг 12. Аналитика проекта — T17

API: `GET /projects/{id}/analytics?period=week|month|all`.

- График «Задачи по колонкам — сейчас»: отображать текущие значения по всем доскам проекта, различать одинаково названные колонки по доске.
- График «Впервые завершено»: временной ряд completion_over_time с серверной гранулярностью и часовым поясом.
- Выбор периода влияет на временной ряд, но не на текущее распределение; явно подписать это.
- Показывать таблицы значений, время формирования, нулевые значения, loading/empty/error.
- Не вычислять агрегаты по карточкам открытой доски и не применять к аналитике ее фильтры.

**Готово:** оба графика используют реальные ответы API, переключение периода работает, повторное завершение задачи не выдается за новое первое завершение.

### Шаг 13. Сквозная проверка и доступность — T19, T21

Проверки добавлять вместе с функциями; здесь собрать общую приемку:

- Unit/component: права, сериализация фильтров, PATCH/null, даты, сохранение черновика при 409, отказ от устаревших снимков, перевод drop в якорь.
- E2E с реальным API и отдельной тестовой PostgreSQL: вход → создание проекта/доски/задачи → изменение → комментарий → перенос → фильтры → аналитика.
- Два независимых browser context: одновременное редактирование, движение карточек, потеря/возврат связи и отзыв членства.
- Проверить закрытие/Back с несохраненными данными, 401/403/404/409/422/429, сеть, долгий ответ и отсутствие двойной отправки.
- На 390/768/1440 px пройти основные действия; проверить клавиатуру, фокус, labels, доступную альтернативу DnD, контраст и reduced motion.
- На демонаборе большого размера проверить скорость доски; вводить виртуализацию только при измеренной необходимости.

**Готово:** пользовательский сценарий проходит через реальный сервер; результаты команд и браузерных проверок сохранены. Mock-тесты не выдаются за интеграцию.

- Обновить README точными командами; оформить `docs/reports/frontend.md` со стеком, деревом, сценариями и реальными снимками Network без секретов.
- Проверить чистый запуск и перезапуск с сохранением данных. Проверку Windows/macOS фиксировать отдельно, только после выполнения на соответствующей системе.

**Готово:** другой участник запускает систему по README; отчет соответствует проверенному коммиту; PR прошел review. Отправка PR, merge и публикация — отдельные действия после реализации.

## 5. Права, которые нужно отразить в интерфейсе

| Действие | Правило |
|---|---|
| Создать проект | Глобальная роль pm или admin |
| Управлять проектом, участниками, досками и колонками | Admin или owner_id текущего проекта |
| Создать/редактировать/двигать задачу, комментировать | Участник проекта, его руководитель или admin |
| Удалить задачу | Admin, руководитель или автор, сохраняющий доступ к проекту |
| Создать тег | Участник, руководитель или admin |
| Переименовать/удалить тег | Руководитель или admin |
| Читать аналитику | Имеющий доступ к проекту |
| Управлять глобальными ролями | Admin; свою роль менять нельзя |

Глобальный pm не управляет всеми проектами. Владелец с глобальной ролью developer сохраняет управление своим проектом. Эти различия подтверждены `services/access.py` и спецификацией. Функции прав управляют видимостью UI; окончательное решение всегда за сервером.

## 6. Ошибки и даты

| Ситуация | Реакция |
|---|---|
| 401 | Завершить локальную сессию, очистить защищенное состояние, открыть вход |
| 403 | Показать отказ; перечитать права при необходимости |
| 404 | «Ресурс недоступен» без раскрытия чужих названий |
| 409 VERSION_CONFLICT | Сохранить черновик, перечитать задачу, предложить сверку |
| 409 POSITION_CONFLICT | Перечитать порядок, предложить повторить перенос |
| Другие 409 | Объяснить конкретное ограничение: дубликат, непустой контейнер и т. п. |
| 422 | Привязать `error.details[].field/message` к полям формы |
| 429 | Учесть Retry-After |
| 503/сеть | Предложить повтор чтения; для write сначала установить фактический результат |

Формат ошибки содержит `error.code`, `message`, `details`, `request_id`. Request ID можно показывать в технических подробностях ошибки.

Deadline — строка календарной даты `YYYY-MM-DD`; ее нельзя превращать в UTC timestamp с возможным сдвигом дня. Просрочку определять по дате в timezone проекта и признаку незавершенности. Временные метки истории — отдельный тип данных; форматировать последовательно с понятным часовым поясом.

1. Основа, сессия и проекты — шаги 0–4, T07.
2. Реальная доска и задача — шаги 5–6, T08.
3. Обсуждение и история — шаг 7, часть T15.
4. Совместная работа — шаг 8, клиентская часть T09.
5. Перенос задач — шаг 9, базовая T11.
6. Фильтры и перенос с фильтрами — шаг 10, T15 и завершение T11.

Шаги 11 и 12 не зависят друг от друга. Шаг 7 можно выполнять до или после базовой интеграции WebSocket, но обновление обсуждения второй сессии проверяется после обоих шагов. Общий API-клиент, router, stores и lockfile должны изменяться согласованно.

Сроки в днях не назначены: неизвестны доступные часы и скорость работы. Оценить оставшийся объем после первой вертикали T07–T08, опираясь на фактическое время и сложности интеграции.

Темную тему, «Мои задачи», быстрые команды и сохраненные фильтры оставить после обязательной приемки. Вложения, чат, спринты, подзадачи, перенос между досками и offline-редактирование не входят в согласованный релиз.
