# Проверка резервного копирования и восстановления PostgreSQL

Проверено 11 сентября 2026 года, 15:26 UTC, на PostgreSQL 18.6 в Windows.
База `tracker` выгружена через `pg_dump -Fc`, архив восстановлен через
`pg_restore --single-transaction --exit-on-error` в отдельную новую базу.
Исходная база продолжала обслуживать приложение и не изменялась проверкой.

В восстановленной базе дополнительно проверены права:

- `tracker` может читать данные и изменять задачи; реальный `UPDATE` одной задачи
  выполнен и отменён через `ROLLBACK`.
- `tracker` может добавлять события аудита, но не может обновлять или удалять их.
- `tracker` не может создавать объекты в схеме `public` или изменять `alembic_version`.
- Попытка владельца `tracker_owner` удалить событие аудита отклонена восстановленным
  триггером с сообщением `audit_events is append-only`; транзакция отменена.

Readiness дополнительно проверена через реальное FastAPI-приложение с runtime-подключением
к восстановленной базе и HTTP-клиентом TestClient. Данная проверка подтверждает доступ
приложения к БД и соответствие версии схемы текущим миграциям; сетевой порт для этой
изолированной проверки не открывался.

## Как повторить

Скрипт [`scripts/verify-backup.py`](../../scripts/verify-backup.py) каждый раз создаёт
имя вида `tracker_restore_<UTC>_<random>`. Он не удаляет существующие базы и не
использует режим очистки при восстановлении. Новая база остаётся для проверки.

Нужны:

- рабочее окружение backend (`uv sync --project backend --frozen`);
- PostgreSQL 18: `pg_dump` и `pg_restore` в `PATH` либо путь через `--pg-bin`;
- корневой `.env` с `DATABASE_URL` и `MIGRATION_DATABASE_URL`, указывающими на одну
  исходную базу;
- отдельный локальный файл с `POSTGRES_ADMIN_PASSWORD` для PostgreSQL-пользователя,
  имеющего право создать новую базу и назначить её владельцем `tracker_owner`.
  При выполненной локальной установке это игнорируемый Git файл
  `work/install/postgres-admin.env` и пользователь `postgres`.

Из корня репозитория в PowerShell:

```powershell
uv run --project backend python scripts/verify-backup.py --pg-bin "C:\Program Files\PostgreSQL\18\bin"
```

При установленных в `PATH` утилитах PostgreSQL команда одинакова для Windows,
macOS и Linux:

```shell
uv run --project backend python scripts/verify-backup.py
```

Другой локальный файл администратора можно выбрать без передачи пароля в аргументах:

```shell
uv run --project backend python scripts/verify-backup.py --admin-env-file /absolute/path/postgres-admin.env --admin-user postgres
```

Пароли читаются из локальных файлов и передаются утилитам через переменную
окружения дочернего процесса `PGPASSWORD`. Скрипт не печатает их и не помещает
в аргументы команд. В терминале выводятся только имя новой базы и путь к результату.

## Артефакты проверки

Локальный каталог успешного запуска:
`work/backups/tracker_restore_20260911_152622_cd7aea/`.

- `tracker.dump` — архив данных и схемы;
- `verification.json` — точные количества, отпечатки таблиц, SHA-256 архива и права;
- `dump.log` и `restore.log` — вывод PostgreSQL-утилит; в успешном запуске оба пусты.

Каталог `work/` исключён из Git. Архив содержит данные приложения, включая хеши
паролей и записи сессий, если они есть; его не следует прикладывать к публичному отчёту.
Для сдачи достаточно этого отчёта и локальной демонстрации выполнения команды.

Проверка подтверждает восстановление текущего учебного набора данных в том же
PostgreSQL-кластере. Автоматическое расписание, внешнее хранилище копий, восстановление
после потери сервера и измерение RPO/RTO требуют отдельных проверок. Запуск через
Docker пока не проверялся, поскольку Windows ожидает перезагрузку после установки WSL.
