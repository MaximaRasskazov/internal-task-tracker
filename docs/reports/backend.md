# Мини-отчет по теме 1: серверная логика

Статус: рабочая основа отчета. Перед сдачей указать проверенный коммит и приложить
снимки именно этой версии. Этот файл сам по себе не подтверждает сдачу или review команды.

## Выбор технологий

Используем согласованный командой FastAPI на Python 3.13. Pydantic проверяет входные
данные и описывает OpenAPI; SQLAlchemy и asyncpg работают с PostgreSQL. Alembic
управляет схемой. `uv.lock` фиксирует точные зависимости для воспроизводимого запуска.

Версии установленного окружения на 11 сентября 2026 года: FastAPI 0.141.1,
Uvicorn 0.52.4, SQLAlchemy 2.0.52, asyncpg 0.31.0, Alembic 1.19.2, Pydantic 2.13.5.
При подготовке окончательного отчета сверить их с lockfile выбранного коммита.

| Решение | Для чего оно нужно | Практическое следствие |
|---|---|---|
| FastAPI и Pydantic | Один набор DTO описывает проверку запросов и OpenAPI для фронтенда | Неизвестные записываемые поля и некорректные значения отклоняются до бизнес-операции; типы клиента можно получить из контракта |
| PostgreSQL | Задачи, участники, колонки и история связаны ограничениями; конкурентные правки требуют транзакций и блокировок | Корректность проверяется настоящей СУБД, включая гонки и внешние ключи |
| SQLAlchemy с asyncpg | Согласованная работа моделей и SQL в асинхронном сервере | Сессия принадлежит запросу; границы commit определяются операцией, а не отдельным SQL-вызовом |
| Alembic | Общая схема должна воспроизводиться у четырех участников без ручной настройки таблиц | Новое ограничение или поле получает миграцию; readiness проверяет соответствие миграций коду |
| uv и lockfile | Windows и macOS должны получать совместимые зависимости | Установка использует зафиксированный набор; обновление библиотеки является отдельным проверяемым изменением |
| Ruff, mypy и pytest | Ошибки оформления, типов и поведения требуют разных проверок | Успех одного инструмента не заменяет остальные; сценарии API запускаются с отдельной PostgreSQL |

## Структура и ответственность

```text
backend/
├── app/
│   ├── main.py           # приложение, middleware, маршруты, lifespan
│   ├── api/              # HTTP/WS-маршруты и транспортные проверки
│   ├── core/             # конфигурация, безопасность и формат ошибок
│   ├── db/               # модели PostgreSQL и асинхронные сессии
│   ├── schemas/          # публичные DTO и проверка входных полей
│   ├── services/         # права, операции над проектами/задачами, аналитика
│   └── cli/              # окружение, bootstrap администратора, seed, OpenAPI
├── migrations/           # версионируемая схема и ограничения БД
├── tests/                # unit и интеграционные сценарии
├── pyproject.toml        # зависимости и настройки проверок
├── uv.lock               # точные версии
└── Dockerfile            # образ API
```

Бизнес-операции проверяют права на сервере. Изменение задачи, аудит и revision доски
сохраняются одной транзакцией; сообщения клиентам отправляются после commit.
Номер версии задачи защищает от потери конкурентных правок. История хранится отдельно
и остается доступна по специальному маршруту после мягкого удаления задачи.

JWT хранится в HttpOnly cookie. Записывающие запросы проверяют Origin и CSRF;
сессии отзываются на сервере. Чужой проект и вложенные ресурсы не раскрываются через API.

## Почему обязанности разделены именно так

Маршруты в `api/` отвечают за HTTP/WS-контракт: параметры, аутентификацию и ответ.
`schemas/domain.py` ограничивает допустимые значения и отделяет клиентские поля от
серверных. Например, клиент передает исполнителя, но автор, номер задачи и timestamps
определяются сервером. `services/` отвечает за права и бизнес-правила. Это позволяет
учебному seed использовать те же операции задач с управляемым временем, сохраняя
правильные версии, аудит и события завершения.

`db/domain.py` фиксирует связи и ограничения хранения, а `db/reads.py` и
`services/views.py` собирают согласованные DTO. Они нужны, чтобы транспорт не зависел
от случайно загруженных ORM-связей и не выполнял отдельный запрос на каждую карточку.
Снимок доски включает revision и связанные данные; согласованное чтение не должно
возвращать новую версию доски вместе со старым списком задач.

`services/access.py` объединяет проверки проекта. Глобальная роль отвечает за общие
возможности, а участие и владение — за доступ к конкретному проекту. Поэтому
developer может работать с задачами своей команды, а PM не получает автоматически
данные всех чужих проектов. Явный доступ admin проверяется на сервере.

## Разбор ключевых операций

### Одновременное редактирование и перемещение

Клиент получает `version` задачи и передает ее как `expected_version`. Если два
участника изменяют версию 3, первая успешная операция сохраняет версию 4. Вторая
получает 409, после чего клиент должен перечитать задачу и показать конфликт.
Слепой повтор запроса мог бы затереть чужую правку, поэтому автоматического
повтора неизвестно завершившейся записи нет.

Для перемещения используется ID следующей карточки `before_task_id`, а не индекс
видимого массива. Фильтр может скрыть часть карточек; сервер вставляет задачу
перед указанным соседом в полном порядке колонки. Позиции хранятся целыми числами
0…n−1. Такой порядок легко проверить после rollback и перезагрузки, но перемещение
может перенумеровать несколько строк. Его производительность следует измерять на
объеме из NFR-02, а не выводить из наличия индекса.

Операции получают блокировки в едином порядке Project → Board → Task. Задача,
история и revision доски изменяются в одной транзакции. Если проверка прав, версии
или связей не проходит, частичный результат не сохраняется. Техническое изменение
позиции соседней карточки не изображается как пользовательское редактирование
ее содержимого.

### Доступ, вход и отзыв сессии

Пароли хранятся как Argon2-хеши. JWT в HttpOnly cookie сопровождается записью
сессии в PostgreSQL: это позволяет прекратить доступ при выходе и не ждать окончания
срока токена. Текущая роль и участие проверяются по сохраненным данным, поэтому
смена роли и удаление участника влияют на следующие запросы.

HttpOnly закрывает чтение cookie из обычного JavaScript, но браузер продолжает
отправлять cookie автоматически. Поэтому для записи дополнительно проверяются
Origin и CSRF-токен. Ответы об ошибках используют общий формат и `X-Request-ID`:
запрос можно сопоставить с журналом, не выводя пароль или строку подключения.

Runtime-пользователь БД отделен от владельца схемы. Приложению не требуется право
отключать защиту истории или менять таблицы; миграции выполняются отдельными
credentials. Append-only защита аудита дополняет ограничения прикладного кода.

### WebSocket и восстановление состояния

Уведомление отправляется после commit, чтобы клиент не увидел изменение, которое
затем откатилось. В сообщении есть revision доски. Снимок из PostgreSQL остается
источником сохраненного состояния: после разрыва клиент запрашивает его заново и
сверяет версии. Heartbeat проверяет актуальную revision и доступ, поэтому потеря
одного уведомления не должна навсегда оставить устаревшую доску.

Текущий hub хранится в памяти одного процесса. Это соответствует запуску API
с одним worker. Для нескольких процессов или серверов потребуется общий канал
доставки событий и пересмотр ограничения частоты входа; простое увеличение числа
workers не является поддержанным способом масштабирования этой версии.

### Аналитика и демонстрационные данные

Распределение по колонкам показывает текущие активные задачи. График завершений
считает первое событие `task.completed` каждой задачи. Если задачу завершили,
открыли заново и завершили повторно, она дает один исторический вклад. Мягкое
удаление также не переписывает прошлые результаты. Границы дней вычисляются
в часовом поясе проекта, а даты событий сохраняются в UTC.

Seed — отдельная команда `python -m app.cli.seed --reference-date YYYY-MM-DD`.
Она создает шесть учебных пользователей, два проекта, три доски, 22 задачи и
помеченную демонстрационную историю. Дата позволяет воспроизвести срок «сегодня»,
просрочку и завершения. Повторный запуск не сбрасывает пароли и не заменяет уже
отредактированную историю. Совпадение с чужими учетными записями или ключами
проекта не означает разрешения присвоить их seed-набору. Production seed запрещен.

## Воспроизводимая проверка

Из корня репозитория после настройки окружения и тестовой PostgreSQL:

```text
python scripts/test-backend.py --integration
```

Тестовая база должна оканчиваться на `_test`. Runtime и schema-owner credentials
передаются отдельно. Интеграционные тесты очищают только явно выбранную тестовую БД;
рабочая база не является подходящим окружением для их запуска.

В отличие от отката одной внешней тестовой транзакции, изоляция через очистку
отдельной БД позволяет API-запросам действительно выполнять commit и проверять
конкуренцию независимых сессий. Перед очисткой проверяются имя `_test` и совпадение
целевой БД двух URL; advisory lock не дает двум процессам одновременно очищать
общие данные. Защита audit-таблицы временно приостанавливается только владельцем
тестовой схемы в транзакции очистки и восстанавливается до запуска сценария.
Для параллельных запусков требуются разные тестовые базы.

Сквозной сценарий `backend/tests/test_acceptance.py` проходит через публичный API:
вход PM, проект и участники, доска и произвольная колонка, теги и задача со всеми
полями, комментарий, перемещение, сочетание фильтров, история и аналитика,
немедленная потеря доступа после удаления участника. Отдельные тесты проверяют
конкурентность, RBAC, WebSocket и ограничения PostgreSQL.

Идентификаторы смысловых коммитов и последующие проверки инфраструктурных утилит
указаны в [сводном отчете](verification.md). Версия кода и материалы фиксируются

Дополнительно зафиксировать результаты Ruff, mypy, проверки миграций и сравнения
экспортированного OpenAPI. Фактические измерения времени ответа, запуск контейнеров,
проход CI на GitHub и проверка на macOS относятся к отдельным доказательствам:
локальный успешный тест не подтверждает их автоматически.

## Материалы для преподавателя

Приложить к одной и той же проверенной версии:

1. Скриншот Swagger с успешным входом и запросом ресурса под участником проекта.
2. Скриншот создания/перемещения задачи с `version`, `board_revision` и `X-Request-ID`.
3. Скриншот запроса чужого проекта с ответом 404.
4. Скриншот успешного запуска тестов и линтера.

На снимках не показывать пароли, cookies, JWT, CSRF и строки подключения.
Материалы БД и инфраструктуры относятся также к темам 2 и 5; фактический запуск
Docker, CI и macOS подтверждается отдельно соответствующим окружением.
