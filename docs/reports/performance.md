# Проверка производительности Backend

Дата проверки: 11 сентября 2026 года. Основание: `product_spec.md`, §14.2.

## Что проверяется и зачем

Проверка показывает, выдерживает ли сервер контрольную учебную нагрузку: 10
аутентифицированных клиентов отправляют в сумме 10 запросов в секунду. Требование
к обычным API-запросам — p95 не выше 1000 мс. Отдельно оценивается p95 каждого
маршрута: быстрые операции не должны скрывать медленную доску или аналитику.

Используется настоящий HTTP-сервер Uvicorn и отдельная PostgreSQL, без подмены
репозиториев, авторизации и SQL-запросов. Время включает локальный HTTP-запрос,
обработку сервером, обращения к БД и получение полного тела ответа клиентом.
Это не замер отрисовки браузером или доставки WebSocket-события.

## Воспроизводимый запуск

Скрипт: `backend/app/cli/benchmark.py`. Нужны Python 3.13, зависимости разработки
из `backend/uv.lock`, работающая локальная PostgreSQL и ранее созданные роли
`tracker_owner` и `tracker`. В корневом `.env` должны быть `DATABASE_URL` и
`MIGRATION_DATABASE_URL`. Они используются только для адреса сервера и учётных
данных: имя базы заменяется на явно указанное `tracker_benchmark_*`.

Из каталога `backend`:

```powershell
uv sync --frozen
uv run python -m app.cli.benchmark --database-name tracker_benchmark_20260911_03 --admin-env ../work/install/postgres-admin.env --output ../work/benchmark-20260911-03.json
```

Та же команда подходит для терминала macOS, если относительный путь ведёт к
существующему локальному файлу с `POSTGRES_ADMIN_PASSWORD`. При каждом повторе
нужно выбрать новое имя базы и новый файл результата.

Пароль администратора не передаётся аргументом командной строки и не выводится
в отчёт. Административная учётная запись используется для создания новой БД.
Миграции и заполнение выполняются владельцем `tracker_owner`, а HTTP-сервер
работает от ограниченной роли `tracker`, как в обычном приложении. Права на
таблицы аудита сужаются миграцией: сервер может добавлять и читать историю.

Защитные ограничения скрипта:

- Разрешены только локальные адреса PostgreSQL и имя по шаблону
  `tracker_benchmark_[a-z0-9_]{1,40}`.
- При существующей БД запуск прекращается; таблицы не очищаются, БД не удаляется.
- Схема создаётся теми же миграциями Alembic, которые использует приложение.
- API запускается отдельным процессом на `127.0.0.1:8010`, с `APP_ENV=test` и
  отдельным случайным JWT-ключом. Занятый порт проверяется до создания БД.
- По окончании останавливается только созданный процесс API. Созданная БД
  остаётся доступной для проверки данных.

## Набор данных

Идентификаторы получаются детерминированно из UUIDv5, структура и распределение
заданы в исходном коде. Пароль нагрузочных пользователей случайный для каждого
запуска; это искусственные аккаунты с адресами `@example.test`.

| Сущность | Количество и распределение |
| --- | --- |
| Пользователи | 20: 2 руководителя проектов, 18 разработчиков |
| Проекты | 2, все 20 пользователей включены в оба проекта |
| Доски | 4: по 2 в проекте |
| Колонки | 40: по 10 на доске, категории todo / in_progress / done |
| Активные задачи | 2000: по 500 на доске и 50 в колонке |
| Завершённые задачи | 400, входят в число активных, `deleted_at IS NULL` |
| Теги | 10: по 5 в проекте, по 2 тега на задаче |
| Связи задача–тег | 4000 |
| Комментарии | 4000: по 2 на задаче |
| Записи истории до нагрузки | 6400: создание, комментарии и завершения |

Назначения, приоритеты, сроки и оценки распределены по задачам. Даты создания
охватывают несколько недель; аналитика читает реальную историю завершений.
Тексты описаний имеют ненулевой объём, поэтому полный снимок доски включает
поля карточек и связи. Перед запуском выполняется PostgreSQL `ANALYZE`, чтобы
планировщик располагал статистикой загруженного набора.

Это синтетическое исходное состояние, загруженное пакетными SQL-вставками, а
не воспроизведение всех исторических действий через API. Начальная версия задачи
равна 1, исходная ревизия доски — 500. Комментарии не меняют версию задачи;
дальнейшие PATCH во время нагрузки проходят обычную проверку версий и создают
настоящие записи аудита.

## Профиль запросов и метод расчёта

Прогрев длится 30 секунд и содержит 300 запросов. После него начинается отдельная
измеряемая фаза длительностью 300 секунд и 3000 запросами. Начальные входы десяти
клиентов и подготовка БД не включаются в обе фазы; повторные входы входят в
измеряемую смесь.

| Группа | Доля | Запросов за 300 секунд |
| --- | --- | --- |
| Чтение полной доски и отдельной задачи | 60% | 1800: по 900 каждого вида |
| Совместные фильтры исполнителя, приоритета, тега, сроков и текста | 20% | 600 |
| Изменение задачи с проверкой версии | 10% | 300 |
| Аналитика проекта за всё время | 5% | 150 |
| Текущая сессия и повторный вход | 5% | 150: по 75 каждого вида |

Последовательность задаётся перестановкой `sequence * 37 % 100`, поэтому в
каждых ста запросах сохраняется точная смесь. Доска меняется каждые сто
запросов, используются оба проекта. Отправка планируется по монотонным часам:
клиент с номером `i` отправляет запрос в `start + second + i / 10`. Задержка
ответа не прибавляется к плановому интервалу следующего запроса.

У каждого клиента своя cookie-сессия и CSRF-токен, одновременно выполняется
не более одного запроса. Каждый клиент изменяет отдельную задачу и берёт
следующую версию из ответа PATCH. Дополнительные скрытые GET-запросы для версии
не выполняются. Это обычная нагрузка; проверки ожидаемых конфликтов и отказов
проводятся отдельно функциональными тестами.

Процентили считаются методом ближайшего ранга: для упорядоченного массива
берётся элемент с номером `ceil(p × N)`. Ошибки HTTP, ошибки транспорта и
таймауты остаются в массиве времени и учитываются в частоте ошибок. Таймаут
одного HTTP-запроса — 10 секунд.

Чтобы фиксированный график отправки не скрывал перегрузку, дополнительно
сохраняются задержка фактической отправки относительно расписания, p95 времени
от планового момента до ответа, фактическая длительность фазы и достигнутое
число запросов в секунду. Все 3000 наблюдений, включая статусы, доступны в JSON.

Успешный код завершения требует отсутствия ошибок, p95 ≤1000 мс суммарно и на
каждом маршруте, 3000 запросов, завершения измерения не позднее 301-й секунды,
p95 задержки отправки ≤100 мс и максимальной задержки отправки ≤1000 мс.
Допуск в расписании учитывает планировщик ОС; он не повышает допустимое время
ответа API. Если сервер быстро отвечает на редкие запросы, но нагрузка отстаёт
от расписания, прогон не считается успешным.

Также сравнивается SHA-256 Python-файлов приложения, миграций и `uv.lock` до
запуска и после измерения. Изменение исходников во время прогона делает его
неприемочным и требует повторения с устойчивой версией.

## Проверка самого нагрузочного инструмента

```powershell
uv run ruff check app/cli/benchmark.py tests/test_benchmark.py
uv run ruff format --check app/cli/benchmark.py tests/test_benchmark.py
uv run mypy app/cli/benchmark.py
uv run pytest tests/test_benchmark.py -q
```

18 тестов проходят без настоящей БД. Они проверяют запрет опасных имён и внешних
адресов, отказ от повторного использования существующей БД, включение ошибок и
таймаутов в процентили, точную смесь HTTP-запросов без скрытых дополнительных
чтений, сохранение исходного расписания при медленном ответе и отказ в успешном
вердикте при недостигнутой нагрузке.

## Границы доказательства

Это локальная проверка Windows без ограничений CPU и памяти; клиент, сервер
приложения и PostgreSQL находятся на одном компьютере. Она не подтверждает
производительность на предложенном стенде 2 vCPU / 4 GiB. Развёртывание в Docker,
другой компьютер, браузерная отрисовка и WebSocket-задержка требуют собственных
проверок. Переносимость команды на macOS не означает, что этот прогон выполнен
на macOS.

В рамках подготовки отдельная БД `tracker_benchmark_20260911_01` была создана,
но измерение в ней не началось: первоначально отсутствовала настройка
database-local прав runtime-роли. После воспроизведения выдачи прав отдельным
шагом выполнен новый запуск в новой БД. Промежуточный прогон `_02` завершился
без ошибок, но использовал `LOG_LEVEL=WARNING`. Приёмочный прогон `_03` повторён
со штатным INFO-журналом запросов; результаты `_02` не подменяют его измерения.
Созданные БД не удалялись; ни `tracker`, ни `tracker_test` этот скрипт не изменяет.
