# Мини-отчет: проектирование и работа с базой данных

## Решение и причины

Используется PostgreSQL 18.6. Предметная область имеет строгие связи: участник проекта,
доска проекта, колонка доски, задача и ее история. SQL подходит для внешних ключей,
уникальности и атомарных изменений нескольких таблиц. Для параллельных переносов важны
настоящие блокировки строк PostgreSQL, поэтому интеграционные тесты не заменяют БД SQLite.

SQLAlchemy 2 async описывает модели и запросы, asyncpg выполняет неблокирующее взаимодействие
с PostgreSQL, Alembic последовательно изменяет схему. Структура не создается вручную в GUI:
новое окружение получает ее через `alembic upgrade head`.

## Структура

```text
backend/app/db/
  base.py       единая metadata и правила именования ограничений
  models.py     три глобальные роли
  domain.py     11 таблиц предметной области
  session.py    runtime engine и жизненный цикл AsyncSession
  reads.py      отдельные согласованные REPEATABLE READ снимки
backend/migrations/
  env.py        async-подключение владельца схемы
  versions/
    20260911_0001_roles.py           роли
    20260911_0002_domain.py          таблицы, индексы, FK и защита аудита
    20260911_0003_runtime_grants.py  ограничение runtime-прав
```

[ER-диаграмма и объяснение слоев](../architecture.md). Модели: `backend/app/db/domain.py`.
Точная схема определяется статическими миграциями; изменение текущей модели не меняет
поведение уже выпущенной миграции.

## Инварианты хранения

| Инвариант | Почему нужен | Как обеспечивается |
|---|---|---|
| Email и ключ проекта уникальны | Нет неоднозначного входа и повторных task key | Нормализация + unique |
| Владелец состоит в проекте | Нельзя оставить проект без управляющего участника | Отложенный составной FK |
| Колонка задачи принадлежит ее доске | UUID в запросе не может переместить задачу в чужой контейнер | Составные FK + сервисная проверка |
| Номер задачи не используется повторно | Публичная ссылка сохраняет смысл после удаления | Счетчик проекта под FOR UPDATE |
| Порядок активных задач целочисленный | Стабильный Kanban без накопления ошибок float | Перенумерация в одной транзакции |
| Удаление сохраняет историю | Действия можно объяснить на защите и при разборе ошибок | deleted_at вместо физического DELETE |
| Аудит только дополняется | Поздние изменения не переписывают прошлые действия | Runtime SELECT/INSERT + trigger |
| Снимок согласован с revision | Клиент не смешивает состояния из разных моментов | Отдельная REPEATABLE READ транзакция |

Для TaskTag соответствие проекта проверяется сервисом внутри той же транзакции. Это
осознанная граница текущей схемы: прямые ручные INSERT от владельца схемы обходят
бизнес-правила и не являются поддерживаемым способом работы приложения.

## Служебные роли

`tracker_owner` выполняет DDL и миграции. `tracker` читает и изменяет разрешенные данные,
не владеет таблицами, не является superuser и не может создавать схему. На `audit_events`
остаются SELECT и INSERT; на `alembic_version` — только SELECT для проверки готовности.
В production-подобном запуске backend-контейнер вообще не получает URL владельца.

## Учебные данные и доказательства

Seed создает шесть пользователей, два проекта, три доски и 22 задачи с разными приоритетами,
сроками, исполнителями, тегами, комментариями и историей. Параметр reference-date делает
календарные случаи воспроизводимыми. Повторный запуск не сбрасывает пароли и не создает дублей.

На нативном PostgreSQL выполнены миграции и seed; `/api/v1/health/ready` возвращает 200.
Проверки ограничений, прав, конкурентности и согласованных снимков входят в общий
[отчет о проверке](verification.md). Результат копирования и восстановления БД фиксируется
в [отдельном отчете](backup-restore.md).

Для сдачи темы приложить ссылку на этот коммит и скриншоты таблиц из pgAdmin/DBeaver
или вывода миграций. Не включать `.env`, пароль, сохраненный профиль подключения и cookie.
Скриншот не заменяет проверку отрицательных сценариев; они сохраняются в тестах.
