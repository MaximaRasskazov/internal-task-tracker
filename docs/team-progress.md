## Ближайшая последовательность

1. Сохранить текущую работу и перезагрузить Windows для активации WSL; PostgreSQL-служба
   запускается автоматически. После перезагрузки запустить Docker Desktop.
2. Из корня выполнить `docker compose up --build --wait backend`, затем `docker compose run --rm seed`.
   Этот запуск использует отдельную контейнерную БД; локальные native-данные не пропадают.
3. [Черновой PR №1](https://github.com/MaximaRasskazov/internal-task-tracker/pull/1) уже открыт.
   Проверить итог Checks текущего head и провести review; слияние пока не выполнялось.
4. Другому участнику запустить проект по README на macOS/своей Windows и отметить реальные
   результаты. При ошибке сохранить команду, код ошибки и окружение без секретов.
5. Подключить frontend по [инструкции](frontend-handoff.md), начиная с сессии и списка проектов.
6. Завершать отчет темы одновременно с соответствующей работающей функцией, чтобы снимки
   и описание не отставали от кода.

## Как оформлять следующие изменения

Одна задача описывает конкретный пользовательский результат и критерий проверки.
Коммит отвечает на вопросы «что изменилось» и «почему это нужно»; его тело фиксирует
важные ограничения и выполненную проверку. Ошибки, найденные при проверке, оформляются
как исправления поведения, а не скрываются за общей фразой «всё готово».

В PR указывать карточку, изменение поведения, способ проверки и связанные документы.
Для API в том же PR обновлять OpenAPI и клиентские типы. Для БД добавлять миграцию,
а при работе с общей используемой БД заранее проверять резервную копию.
Смежные роли команды сохраняются: разделение модулей помогает избежать конфликтов,
но не отменяет совместного понимания продукта и перекрестного review.
