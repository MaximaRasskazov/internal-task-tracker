# Командный план Mini-Jira / Kaiten

Версия плана: 1.0. Это законченный план разработки и проверки, а не отчет о выполненной реализации. Код, репозиторий, замеры и скриншоты еще предстоит подготовить.

## 1. Основа плана

Подтверждено командой: FastAPI на сервере, Vue.js на клиенте; существующий репозиторий пока без кода; макетов нет; разработка через Claude Code на Windows и macOS. Проверен [репозиторий internal-task-tracker](https://github.com/MaximaRasskazov/internal-task-tracker): default branch — `release`, на момент подготовки есть только `README.md`. В команде Казаков Виталий, Рассказов Максим, Исмагулов Саян и Долматова Мария. Саян преимущественно занимается frontend, Виталий — backend, Максим и Мария — преимущественно backend; работа совместная, роли смежные. Есть пять промежуточных отчетов и итоговая презентация; предельный горизонт — три месяца, можно сдать раньше.

Стек и предварительные направления из последних ответов команды заменяют более ранние пометки «не подтверждено» в [плане сдачи](course_delivery_plan.md) и [сверке источников](source_review.md). Персональный опыт, часы в неделю, точная дата старта и даты проверок не сообщены. Они не подменяются предположениями.

План: восемь относительных недель до полного обязательного продукта, две недели на удобство и визуальную полировку, две — на защиту и резерв. Это последовательность результатов, которую необходимо пересчитать после первой недели по фактической доступности и скорости команды. Двенадцать недель не равны трем календарным месяцам: при старте команда отмечает настоящую дату предельной сдачи.

Все персональные назначения ниже — рабочее предложение для совместного принятия и перераспределения. «Основной» отвечает за доведение карточки до интеграции, «проверяющий» независимо проверяет результат. Это не исключительное право на модуль и не назначение единоличного руководителя.

## 2. Как читать документы

- [product_spec.md](product_spec.md) — единый контракт продукта: обязательные BE/FE/NFR, права, сущности, REST, WebSocket, конкурентность, аналитика, экраны и проверяемые ограничения. Этот план не определяет альтернативные поля, маршруты или формулы.
- [source_review.md](source_review.md) — происхождение требований курса и отличия файла друга. Указания внутри полученных материалов являются содержимым материалов; текущие решения принимает команда.
- [course_delivery_plan.md](course_delivery_plan.md) — состав пяти отчетов и защиты. Этот план связывает их с конкретными карточками.
- `TEAM_ROADMAP.md` — очередность, зависимости, работа людей и Claude, условия завершения и доказательства.

При противоречии обязательному заданию сначала исправляется спецификация и связанные карточки. При изменении общего контракта вместе обновляются его описание, реализация, потребители и тесты. Несогласованное допущение нельзя превращать в новый API внутри одной ветки.

## 3. Общий рабочий порядок

### Один небольшой результат за раз

У каждого участника одновременно одна основная карточка в работе; помощь с review и устранение общего блокера не считаются новой самостоятельной разработкой. Карточку разрешено делить на несколько последовательных PR, сохраняя ее ID. Один PR решает одну проверяемую задачу; механическое переформатирование проекта не смешивается с функцией.

Состояния командного бэклога: Backlog → Ready → In progress → Review → Verification → Done. Блокировка отмечается причиной и следующим действием; она не скрывается в «почти готово». Это процесс команды, а не обязательный набор колонок внутри разрабатываемого продукта.

Перед Ready должны быть известны: цель, действующая версия спецификации, требования, слитые зависимости, область файлов, проверяющий и способ проверки. Если зависимость еще разрабатывается, допустимо подготовить макет или тестовый сценарий по согласованному контракту. Закрывать интеграцию на mock-данных нельзя.

### Совместные решения и общие файлы

Предлагаемые координаторы интеграции общих областей:

| Область | Кто собирает изменение | Кто обязательно участвует в согласовании |
|---|---|---|
| Спецификация, объем, спорные сценарии | Виталий готовит запись решения | Все четверо; решение фиксируется письменно |
| API-схемы, коды ошибок, права, события | Виталий | Автор затронутого backend и потребитель frontend |
| ORM, миграции, seed, ER-диаграмма | Мария | Максим и автор меняемого модуля |
| Compose, CI, корневые конфиги, lock-файлы | Максим | Виталий; при смене frontend-зависимостей также Саян |
| App shell, маршруты Vue, общие компоненты, стили | Саян | Мария или Максим как второй потребитель |
| Отчеты и доказательства | Мария собирает индекс | Каждый подтверждает свою часть; Максим проверяет ссылки |

Координатор помогает избежать одновременных правок и не получает права единолично менять общий объем. Существенное решение публикуется коротко: проблема, выбранный вариант, затронутые карточки, последствия, участники согласования. Все четверо подтверждают изменение общего объема; контрактные изменения подтверждают владельцы обеих сторон. Текущий ведущий общего демо меняется по кругу: Виталий → Максим → Мария → Саян.

Общие миграции, lock-файл или корневой router одновременно меняет одна карточка. Зависимые PR обновляются после ее слияния. Для миграций проверяют фактическую цепочку и запуск на новой БД; конфликтующие autogenerated revision нельзя сливать механически. Смена пакета требует проверки команды запуска, lock-файла, CI и инструкций для обеих ОС.

### Ветки и Claude Code

Каждый человек и одновременно работающий Claude используют отдельный clone или Git worktree и свою ветку. Два Claude не редактируют одну рабочую директорию; разные ветки в общей директории этого не исправляют. Название ветки содержит ID, например `feature/T13-comments-history`; короткий PR направляется в существующую общую ветку `release`. Новые `main` или `develop` для этого процесса не нужны. Запрещены переписывание общей истории и force-push в `release` без отдельного согласованного решения команды.

В начале сессии Claude получает выбранную карточку, `product_spec.md`, этот план, состояние зависимостей и допустимую область файлов. Человек просматривает diff, проверяет поведение и способен объяснить написанный код. Ответ Claude «все готово» без выполненных проверок не закрывает карточку.

В PR указываются: ID и конкретное изменение поведения; затронутые требования; изменение контракта, если оно есть; реальные команды проверок и результат; для интерфейса — скриншот и проверяемый сценарий. Автор не одобряет свой PR вместо проверяющего. Слияние идет после проверки другим участником и зеленого обязательного CI. Возможность технически включить branch protection зависит от настроек репозитория; договоренность о review действует в любом случае.

### Общий Definition of Done

1. Реализованы цель и границы карточки по текущему контракту; нет заглушек в сдаваемом сценарии.
2. Проверены успешный путь и существенный отрицательный/пограничный случай. Серверные полномочия проверены для затронутых защищенных операций.
3. Выполнены относящиеся к изменению линтер, форматирование, сборка и тесты; результаты указаны честно, не выполненное явно обозначено.
4. Изменение прошло независимый review, слито в общую ветку и проверено в объединенной версии.
5. Контракты, README, миграции и связанные доказательства обновлены там, где изменение их затрагивает.

Инфраструктурная карточка может проверяться чистым запуском, логом, тестом или CI; обязательный UI-клик для нее не нужен. Серверный endpoint может иметь собственную API-приемку до появления экрана. Готовность продукта в целом требует полного пользовательского демо через реальный интерфейс без ручного редактирования БД.

## 5. Карточки T00–T27

Номера BE/FE/NFR взяты из задания и расшифрованы в `product_spec.md` и `source_review.md`. Прямые зависимости совпадают с таблицей §18 `product_spec.md`; транзитивные зависимости отдельно не добавляются. Зависимость означает, что соответствующий контракт и необходимый код слиты до завершения зависимой карточки. В карточках тестирования и документации работа начинается раньше, а перечисленные зависимости определяют момент итоговой приемки. T11 начинается после T08/T09/T10 и завершается проверкой DnD с фильтрами после T15; T15 не ожидает полного закрытия T11. Серверная приемка T10 и T13 не требует готового WS-транспорта T09: доставка событий в браузер проверяется при общей интеграции.

### T00 — Зафиксировать основу и контракты

- **Цель:** дать четырем разработчикам одну версию требований, данных, прав, API, событий и UI-сценариев.
- **Требования:** все BE/FE/NFR; особенно NFR-06 и NFR-07.
- **Зависимости:** нет.
- **Основной / проверяющие:** Виталий собирает; Максим, Мария и Саян проверяют свои потребители и весь объем.
- **Границы:** спецификация, журнал решений, исходный бэклог и простые макеты основных экранов. Не писать независимые версии контракта в отдельных ветках.
- **Done:** команда прошла путь «проект → доска → задача → изменение → второй пользователь → аналитика» по документам; спорные решения не блокируют T01–T09; требования сопоставлены с карточками; актуальная версия попала в репозиторий.

### T01 — Репозиторий, инструменты, минимальные CI и Compose

- **Цель:** одинаковая запускаемая основа на Windows и macOS с автоматической проверкой каждого PR.
- **Требования:** NFR-06, NFR-08.
- **Зависимости:** T00.
- **Основной / проверяющий:** Максим / Виталий.
- **Границы:** структура проекта, фиксируемые зависимости, пример переменных окружения без секретов, минимальные сервисы Compose, линтеры, базовая сборка и CI. Версии берутся из спецификации, а фактическая совместимость проверяется.
- **Done:** каждый участник воспроизводит старт; клиент и сервер доступны, БД здорова; минимальный workflow проходит; README описывает PowerShell и macOS-путь без Windows-only предположений. T22 позднее добавляет полный стек и весь suite.

### T02 — Схема, миграции и демонстрационные данные

- **Цель:** постоянное согласованное хранилище для первой вертикали и последующих модулей.
- **Требования:** BE-03–BE-08, NFR-03, NFR-06, NFR-08.
- **Зависимости:** T01.
- **Основной / проверяющий:** Мария / Максим.
- **Границы:** ORM и миграции по модели спецификации, индексы и ограничения, seed, ER. При дальнейшем расширении схема меняется отдельной согласованной миграцией через эту область ответственности.
- **Done:** пустая БД разворачивается до актуальной версии; повторный предусмотренный запуск seed не создает неконтролируемых дублей; связность данных и проектные границы проверены; демонстрационные учетные записи и ожидаемые данные описаны; нет ручных SQL-исправлений для запуска приложения.

### T03 — Аутентификация и административные роли

- **Цель:** войти в систему и применять серверные роли без возможности самоповышения.
- **Требования:** BE-01, BE-02, NFR-03, NFR-04, NFR-07.
- **Зависимости:** T02.
- **Основной / проверяющий:** Виталий / Мария.
- **Границы:** пароль, токен и жизненный цикл сессии, назначение ролей и их проверка по спецификации. UI управления реализуется T18.
- **Done:** проверены успешный и неуспешный вход, отсутствующая/недействительная сессия, назначение роли администратором и отказ обычному участнику; пароль хранится стойким хэшем; ответ и логи не раскрывают пароль или токен; роль нельзя повысить изменением обычного профиля.

### T04 — Проекты, участники и изоляция доступа

- **Цель:** управлять проектом и его составом с едиными серверными полномочиями.
- **Требования:** BE-03, NFR-01, NFR-04, NFR-07.
- **Зависимости:** T03.
- **Основной / проверяющий:** Виталий / Максим.
- **Границы:** проекты, членство и переиспользуемые проверки доступа. Точные полномочия и поведение при удалении участника задает `product_spec.md`.
- **Done:** PM выполняет разрешенные операции; участник видит только допустимые проекты; обращение постороннего по известному ID отклонено; удаление участника отражается в последующих проверках прав. Тесты проверяют сервер, а не только скрытие кнопок.

### T05 — Доски и произвольные колонки

- **Цель:** иметь несколько досок проекта с управляемыми упорядоченными колонками.
- **Требования:** BE-04, NFR-03, NFR-04, NFR-07.
- **Зависимости:** T04.
- **Основной / проверяющий:** Максим / Виталий.
- **Границы:** доски и колонки, порядок и разрешенные изменения по контракту; согласование статуса завершения с аналитикой. Не вводить жестко зашитые три колонки вместо кастомных.
- **Done:** создаются две доски с разными колонками; порядок сохраняется после повторного чтения; проверены конфликтующие/запрещенные изменения и операции над непустой колонкой по спецификации; нельзя связать сущности разных проектов.

### T06 — Задачи и аудит в одной транзакции

- **Цель:** сохранять обязательные поля задачи и историю изменений как один согласованный результат.
- **Требования:** BE-05, BE-08, NFR-01, NFR-03, NFR-04, NFR-07.
- **Зависимости:** T05.

- **Done:** задача создается коротким путем с корректными обязательными данными; «Мои задачи» показывает только доступные задачи текущего пользователя по согласованной семантике; клавиши не мешают вводу текста и имеют обычные кнопочные альтернативы; тема сохраняется локально и не нарушает читаемость; основные сценарии проходят повторно; команда подтверждает сокращение лишних действий на конкретном примере.

### T26 — Условные улучшения: WIP-подсказки и личные фильтры

- **Цель:** сделать перегрузку колонки заметной и упростить повторное использование поиска при наличии реального резерва.
- **Требования:** необязательные продуктовые улучшения; сохранение BE-07/BE-09, FE-02/FE-03, NFR-04/NFR-09.
- **Зависимости:** T25 и пройденный gate недели 8; отдельное совместное решение о включении в объем.
- **Основной / проверяющий:** Максим / Саян; Мария помогает с отдельными UI-компонентами.
- **Границы:** каждое улучшение — отдельный PR и отдельное решение о включении. Используется §16.2 `product_spec.md`: WIP является мягким предупреждением; пресеты — личные локальные данные браузера с областью user_id+board_id. Принятое расширение DTO/модели WIP фиксируется в версии спецификации перед реализацией.
- **Done для WIP:** лимитом управляют разрешенные роли, счетчик и предупреждение соблюдают контракт, перемещения не блокируются; параллельные move и filtered view проверены. **Done для фильтров:** сохранение/применение воспроизводит параметры, учитывает пользователя и доску, не раскрывает чужие данные и корректно обрабатывает устаревший пресет. Не принятая подфункция явно исключается из релиза, а не остается «наполовину».

### T27 — Финальная проверка и передача

- **Цель:** передать одну целостную версию с доказательствами и понятным запуском.
- **Требования:** все обязательные BE/FE/NFR и материалы курса.
- **Зависимости:** T24; все взятые в релиз T25/T26 завершены или явно исключены.
- **Основной / проверяющие:** Виталий собирает проверку / Максим, Мария и Саян подтверждают свои и смежные сценарии.
- **Границы:** финальный commit и при принятой конвенции tag, список включенного объема, проверка ссылок и инструкций, открытые некритичные ограничения, резервная копия материалов. Незавершенная экспериментальная ветка не считается частью продукта.
- **Done:** обязательные критерии закрыты доказательствами; полный запуск и демо прошли на выбранной версии; отчеты, презентация и исходники соответствуют ей; каждый может получить код и объяснить, как восстановить работу. Ни один блокирующий дефект не помечен готовым ради даты.

## 6. Разгрузка frontend и сохранение общего понимания

Единственный основной frontend-разработчик — главный риск критического пути. Решение заложено в карточки: Саян делает shell, доску, DnD и общую адаптивность; Мария берет интерфейс фильтров/комментариев/истории и графики; Максим — управляющие формы. Их backend-направление сохраняется, но не превращается в запрет работать во Vue.

На первой неделе Саян вместе с Марией и Максимом собирает одну общую форму и показывает API-клиент, состояние запроса, обработку ошибки и правила компонентов. После этого помощь идет отдельными UI-модулями с ограниченными файлами. Саян не должен переписывать их PR: общие правила фиксируются один раз, review назначается короткими согласованными окнами. При очереди более двух UI-PR команда сначала разгружает review, затем начинает новые экраны.

| Риск | Ранний сигнал | Конкретная реакция |
|---|---|---|
| Очередь на Саяна | Backend готов, а несколько экранов ждут одного человека | Мария забирает T15/T17, Максим — T18; заморозить новые стили/компоненты до согласования основы. |
| Неизвестная занятость | Первая неделя закончилась, доступные сессии не записаны | Каждый сообщает реальную доступность на следующую неделю; пересчитываются WIP и последовательность, а не выдумываются часы. |
| Разные API у разных Claude | Несовпадающие имена полей, права или события в соседних PR | Остановить только затронутую интеграцию; совместно исправить контракт и потребителей в небольшом связанном наборе PR. |
| Позднее обнаружение сложных WS/гонок | «Realtime сделаем в конце» или тест только одного окна | Вернуть T09 в gate недели 3 и T10 в неделю 4; отложить дополнительный дизайн до работающей вертикали. |
| Один человек понимает свой модуль | Проверяющий не может воспроизвести или объяснить PR | Короткая передача сценария и инвариантов; повторный review другим участником; владелец остается доступен для вопроса. |
| Документы отстали | ER/OpenAPI/README не совпадают с текущим кодом | Обновлять вместе с PR; еженедельно проверять одну тему отчета на текущем commit. |
| Различия Windows/macOS | Команда запускается только у автора | Проверка T01 обеими платформами и повтор T22; корректируются пути, команды и доступность архитектур образов. |
| Увлечение дополнительными фичами | T25/T26 начались при красном обязательном gate | Приостановить дополнительный объем, закончить обязательные дефекты и доказательства; вернуться только при свободном резерве. |

Рабочий ритм согласуется под реальную доступность: короткая асинхронная запись при начале/конце своей сессии («сделано / следующее / блокер»), оперативный разбор блокера с затронутым участником и одно общее демо в неделю. Демо показывает объединенный commit, а не четыре отдельные локальные версии. После демо записываются gate, дефекты, решения и следующие Ready-карточки.

## 8. Как начать каждому

### Общий старт

1. Перенести согласованный комплект документов в [internal-task-tracker](https://github.com/MaximaRasskazov/internal-task-tracker) и всем открыть одну версию. Использовать существующую общую ветку `release`; проверить права участников.
2. Совместно пройти T00: зафиксировать объем первой вертикали, ключевые макеты и право на общие файлы. Подтвердить или переназначить предложенные роли карточек.
3. Получить отдельную рабочую копию на каждого и завести ветки конкретных карточек. Claude начинает только с выбранной карточки и ее границ.
4. Выполнить T01, после чего проверить запуск всеми четырьмя; затем развивать T02/T07 и контракты первых серверных модулей параллельно.
5. В конце первой недели записать фактическую доступность и пересчитать ближайшие две недели. План следующих этапов уточнять на каждом gate.

### Первые действия Виталия

Собрать T00 с командой; проверить T01 у Максима. После T02 выполнить T03, затем T04 и T06 небольшими PR. Для T09 заранее проверить протокол и место публикации события после commit с Саяном и Максимом. На gate недели 3 провести вместе с Саяном реальный сквозной сценарий двух пользователей.

### Первые действия Максима

Взять T01; заранее проверить команды на обеих платформах с их владельцами. Проверить схему и миграции T02. После T04 реализовать T05, затем T10/T12/T14 в очередности, необходимой frontend. До T18 вместе с Саяном освоить общую форму и API-клиент; управляющие экраны сделать самостоятельно в согласованной области. Расширять CI вместе с появлением тестов.

### Первые действия Марии

Взять T02 по утвержденной схеме; подготовить seed, пригодный для прав, двух окон и аналитики. Проверить T03/T06. Затем вести T13 и T16; согласовать с Саяном разбиение T15/T17 и не ждать окончания всего backend для знакомства с Vue. С первого этапа собирать реальные доказательства в индекс отчетов.

### Первые действия Саяна

В T00 согласовать с командой основные экраны, их состояния и компоненты; затем T07. Перед интеграцией T08 пройти с Виталием формы и ответы API, затем подключить WS-клиент T09. Сфокусироваться на доске, DnD и мобильном поведении. Передать Марии и Максиму правила отдельных UI-модулей и проверять их в согласованные окна, сохраняя время на критический путь.

## 9. Ограниченные задания для Claude Code

Эти запросы запускаются в собственной рабочей копии участника. Указанные зависимости должны быть слиты или явно обозначены как еще не готовые. Примеры не являются просьбой выполнить весь проект в одной сессии.

**Для backend, карточка T06:**

> Прочитай product_spec.md и T06 из TEAM_ROADMAP.md. Проверь фактическое состояние T02–T05 в этой ветке. Реализуй только операции задач и транзакционный аудит в границах T06, соблюдая существующие API-схемы и права. Не меняй контракт самовольно: если реализация противоречит документу, укажи конкретное расхождение и предложи минимальное согласованное исправление. Добавь проверку отката задачи при сбое записи истории и проверку межпроектной связи. Выполни относящиеся проверки и дай краткий diff-отчет: поведение, файлы, результаты и не выполненное. Не помечай интеграцию завершенной без реальной БД.

**Для frontend, карточка T15:**

> Прочитай product_spec.md, T15 и общие правила Vue в репозитории. Выполни только UI фильтров, тегов, комментариев и истории. Используй существующие API-клиент, формы и состояния; shell и механизм DnD не перерабатывай. Проверь работу трех фильтров одновременно, сброс без изменения данных, сохранение комментария и повторную загрузку по реальному API. T15 не ждет полного закрытия T11: передай готовые фильтры для его итоговой проверки; обновление второй сессии затем проверяется в T21. Если endpoint еще не готов, опиши блокер, а самостоятельный макет не выдавай за интеграцию. После реализации выполни сборку и относящиеся проверки, перечисли фактически проверенные сценарии.

**Для инфраструктуры, карточка T01:**

> Прочитай product_spec.md и T01. Подготовь минимальную основу FastAPI/Vue с БД, Compose и CI в пределах выбранного стека. Возьми версии и структуру из спецификации; все новые зависимости отрази в lock-файлах и README. Проверь команды в доступной среде, отдельно обозначь, какая из Windows/macOS фактически не проверена. Не добавляй бизнес-функции из T03–T18. Не включай секреты в код и не используй удаление постоянных данных как обычный способ запуска.

**Для независимого review T10:**

> Проверь diff карточки T10 по product_spec.md и ее Done. Сопоставь атомарность, порядок, ревизии, аудит и публикацию событий с контрактом. Воспроизведи два одновременных перемещения и отказанный запрос на тестовых данных. Не вноси посторонний рефакторинг. Верни только конкретные дефекты с условиями воспроизведения и фактические результаты проверок; если все проверки прошли, так и напиши без выдуманных замечаний.

**Для отчета темы 2, карточка T23:**

> Подготовь отчет темы 2 по действующей реализации и ее commit. Возьми настоящие миграции, ORM, структуру и ER; сверь связи с кодом. Перечисли необходимые скриншоты и используй только уже полученные доказательства. Отсутствующую ссылку, запуск или screenshot пометь как не подготовленные; ничего не выдумывай. Отчет должен позволять преподавателю проверить выбранную БД, схему и сохранение данных.

## 10. Когда продукт можно сдавать

Полный обязательный объем из `product_spec.md` реализован, все BE/FE/NFR имеют воспроизводимое подтверждение, объединенная версия запускается по README на Windows и macOS, CI проходит на финальном commit, пять отчетов и презентация совпадают с кодом. Команда показывает продукт через UI, понимает его данные, полномочия и конкурентные изменения. Дополнительные функции приняты и проверены либо явно исключены из релиза. Если эти условия выполнены раньше двенадцатой недели, резерв ждать не требуется.
